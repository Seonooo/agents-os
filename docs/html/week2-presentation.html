MOVE 01 — 테제
왜 프롬프트가 아니라 harness인가
RAW 인용
Addy Osmani — Agent Harness Engineering
"A decent model with a great harness beats a great model with a bad harness."
모델은 못 바꾼다. 바꿀 수 있는 leverage는 전부 harness에 있다 — behavior-first 설계.
우리 작업 적용
.agent-os/ 구조 전체가 이 등식의 구현체.
  • .agent-os/loop.md — 반복·검증 절차
  • .agent-os/harness.md — 7-check 검증 항목
  • .claude/skills/ — 재사용 패턴 4종
  • 이번 주 core/ vs root 분리로 "harness를 이식 가능하게"까지 확장
MOVE 02 — 비용의 수학
"작게 자른다"는 취향이 아니라 수학
RAW 인용
OpenAI — Unrolling the Codex Agent Loop
"The agent loop is quadratic in terms of the amount of JSON sent to the Responses API over the course of the conversation."
세션 길이 2배 → 토큰 4배. 매 턴 이전 메시지·툴콜이 전부 다시 들어가기 때문.
우리 작업 적용

  • 실증: post-comments task를 처음에 POST+GET+entity+컬럼으로 묶었다가, "Week 2는 잘게 쪼개기"라는 지적으로 post-comments-create(POST만)로 분할
  • 한 사이클 결정 8개 → 5개로 축소
  • post-search도 같은 이유로 의도적 1-endpoint 크기

정직한 갭

잘된 것보다 안 된 것이 발표의 핵심.

인용이 우리 자신을 친 지점

harness.md 95줄 — Osmani가 권장한 "60줄 이하 체크리스트"를 우리가 초과. 7-check 라벨링 비용. → retro action: 라벨 유지하고 본문 압축해 70줄 목표.
Harness manual walk의 self-bypass — 구현 단계에선 자동 체크만 돌리고 7-check 수동 검토는 커리큘럼이 강제할 때까지 안 함. → MOVE 06의 Stop hook이 이걸 처방.
batch json over-engineering — 5줄 변경에 batch 작성은 ceremony 비용 > discipline 가치. 임계점 발견: 3파일↑ 또는 마이그레이션 포함 시에만.
잠정안의 conservative bias — anchoring 데이터 4/6. 사용자 수정 3건이 전부 "줄이는" 방향(title only·escape drop·N+1). 잠정안이 늘 "안전한 over-spec"으로 치우치는 경향 발견.
7주간 agent-os의 Spring 종속을 못 알아챔 — 자체 audit 트리거가 없었음. 사용자 지적이 없었으면 영구히 그 상태. → core/ 분리로 처방.
모델을 더 세게 시키려 하지 말고 검증 구조를 만들어라.
그리고 그 구조가 사람 기억에 의존하면 무너진다 —
그래서 마지막에 hook으로 시스템에 박았다.
