## 1. AI Summary (사전 이해)

### Task goal
게시글 전체를 일정한 순서로 반환하는 단순 목록 조회 엔드포인트(`GET /posts`). 페이지네이션·검색·필터는 의도적으로 범위 밖. 이 작업으로 MVP 두 엔드포인트(작성/조회)가 완성됨.

### Change scope
- 수정 4개 파일: `PostController`(`@GetMapping` 1개), `PostService`(`list()` 추가), `PostServiceTest`(단위 추가), `PostControllerE2ETest`(E2E 추가)
- 선택적 수정 1개: `PostRepository`에 `findAllByOrderByCreatedAtDesc()` 시그니처 추가
- 신규 파일·의존성·Flyway 마이그레이션 없음
- 기존 패턴 100% 재사용

### Acceptance criteria (핵심)
- `GET /posts` → `200 OK` + JSON 배열, 항목당 7필드 그대로
- 정렬 = `createdAt` DESC (잠정)
- 빈 상태 = `200 + []`
- `viewCount` 증가 없음, DB 상태 불변
- 회귀 금지: 기존 9개 테스트 그대로 통과

### Risks watched
- 결과 무제한 반환 — 글 수 증가 시 응답이 비대 (Performance 섹션에 명시)
- 정렬 안정성 — 동일 createdAt에서 순서 불안정 가능 (Q-D)
- 테스트 데이터 결정성 — 동일 Clock 호출 시 ms 차이 부재 가능 (Q-E)
- N+1 쿼리, 풀스캔 — MVP 범위에서 수용

### Interpretive points (I1~I8)
| # | AI 해석 |
|---|---|
| I1 | URL: `GET /posts` (POST와 같은 path) |
| I2 | Service: `public List<PostResponse> list()`, 인자 없음 |

| I4 | `@Transactional(readOnly = true)` 권장 |
| I5 | `Clock` 미사용 (시간 의존 없음) |
| I6 | 테스트 시드는 `PostRepository.saveAll(...)` 직접 |
| I7 | 단위 테스트는 매핑·순서 보존만 검증 |
| I8 | 실제 정렬 검증은 E2E 책임 (DB 위임) |

### Outstanding questions (L1~L6 + Q-D/E/F)
- L1 응답 형식, L2 정렬, L3 결과 제한, L4 viewCount 증가, L5 빈 목록, L6 Repository 메서드
- Q-D 동일 createdAt 정렬 안정성
- Q-E 정렬 검증을 위한 테스트 시간 결정성
- Q-F Service 반환 타입(List vs Page)

## 2. Human Review (2026-05-16)

### 🔴 Major correction — Pagination should be applied

> "페이지네이션 적용하는게 맞아보이는데?"

**원래 Task Context는 페이지네이션을 Forbidden으로 박아두었지만, 이 결정을 사용자가 뒤집었다.**

#### 근거 (사용자가 명시하지 않았으나 합당한 추론)
- 실제 게시판은 글이 누적되며 무한정 자라는 자원. 전체 반환은 학습용으로도 곧 불편해진다.
- POST Task Context의 "페이지네이션 금지"는 POST 작업의 단순화 목적이었지, 시스템 정책으로 굳힐 의도는 아니었다. GET 작업에서는 재평가해야 했다.
- AI가 "POST와 일관"이라는 표면적 일관성에 안주해 진짜 필요를 못 본 사례.

#### 영향 (Cascading effects)
- Task Context의 다음 항목이 모두 영향을 받음:
  - Goal — "전체를 일정한 순서로 반환" → "페이지 단위로 반환"
  - Forbidden — "페이지네이션 추가 금지" 항목 제거
  - Change Scope — 신규 파일 `PageResponse.java` 추가
  - Acceptance Criteria — page/size 파라미터, 기본값, 최대 size, 응답 형식 추가
  - Verification — curl 예시에 `?page=`, `?size=` 추가
- 부수 효과: Q-D(정렬 안정성), Q-E(테스트 결정성), Q-F(반환 타입)가 페이지네이션 결정에 의해 자연스럽게 함께 해결됨

#### Lesson
AI는 "이전 결정과의 일관성"을 너무 쉽게 우선하는 경향이 있다. 사용자가 "다음 작업"으로 넘길 때 **이전 결정을 재검토하는 단계**를 워크플로에 명시적으로 두어야 한다는 점. `AGENTS.md` 또는 `context-template.md`에 "이 작업이 이전 작업의 어떤 결정을 뒤집어야 하는가?" 항목을 두는 것이 후속 개선안.

### Pagination spec — P1~P4 권장안 채택

| # | 결정 | Task Context 적용 위치 |
|---|---|---|
| P1 | 커스텀 `PageResponse<T>` record (`content, page, size, totalElements, totalPages`) | Change Scope: 신규 파일 `PageResponse.java` / Acceptance: 응답 형식 |
| P2 | 기본 size 20, 최대 size 100 | Acceptance: 파라미터 기본값과 검증 / Forbidden: size>100 허용 금지 |
| P3 | 고정 `createdAt DESC`, `sort` 파라미터 미지원 | Acceptance / Forbidden: sort 파라미터 지원 금지 |
| P4 | `createdAt DESC, id DESC` 보조 정렬 | Acceptance: 정렬 규칙 |

### Side effects on prior open questions

| # | 원래 질문 | P1~P4로 해소 |
|---|---|---|
| L1 | 단순 배열 vs 페이지 객체 | **뒤집힘** — 페이지 객체(PageResponse) 채택 |
| L2 | 정렬 방향 | createdAt DESC (P3) |
| L3 | 결과 제한 | size 파라미터로 제한, 기본 20·최대 100 (P2) |

### Interpretive points (I1~I8) 검증
- I1 (URL: GET /posts), I4 (readOnly), I5 (Clock 미사용), I6 (saveAll 시드), I7 (단위는 매핑만), I8 (정렬은 DB 위임) — **유지**
- I2, I3 — **뒤집힘**:
  - I2 → Service 시그니처: `PageResponse<PostResponse> list(int page, int size)`
  - I3 → Controller 반환: `PageResponse<PostResponse>` 직반환

## 4. Learning notes

- **AI가 "이전 결정과의 일관성"에 안주한 사례.** POST Task Context의 "페이지네이션 금지"를 그대로 GET에 복제했고, "GET 목록 조회에 페이지네이션이 필요한가?"라는 본질적 질문을 던지지 않았다.
- **사용자의 단 한 줄 교정("페이지네이션 적용하는게 맞아보이는데?")이 6개의 잠정 결정(L1~L6)과 3개의 후속 질문(Q-D/E/F)을 한꺼번에 무력화하고 더 단순한 결정 트리로 바꾼다.** 좋은 교정은 미세 조정이 아니라 가정 자체를 흔든다.
- **개선안**: `context-template.md` 또는 `AGENTS.md`에 "이 작업이 이전 작업의 어떤 결정을 재평가해야 하는가?" 섹션을 후속으로 추가 검토. 단, 이번 작업 범위 밖.
- **deliverable 양식**: POST 때 만든 `.review.md` 구조(AI Summary → Human Corrections → Trace → Learning notes)가 그대로 재사용 가능했다. 양식의 재사용성 확인.
